# 生成统一重构施工图(统一入口 + 单一状态真相)

> 目标:让「卡片生成」这件事 **入口唯一、状态真相唯一、翻译逻辑唯一**,使手点 / 组运行 / agent / 对话面板 / 失败重试五条路径行为完全一致,从结构上杜绝「组跑和手点不一致」「按钮没禁用」「状态/进度不显示」这类问题。
>
> 本文是施工图,供分模块、可跨会话精确接续执行。每一步都标了源文件:行号与验证点。

---

## 一、根因:两个分裂

1. **入口分裂**:同一个「生成」有 4 套实现 —— 5 个编辑器各写一份 `handleGenerate`(共 ~850 行,十步骨架复制五遍);`cardRunner`(组运行/agent 本该共用的统一层)只做了一半;agent / 对话面板走 legacy 直连不落 task。
2. **状态分裂**:判断「卡在不在生成」要 OR 4 个来源(`generatingCards` / `groupRunStatus.currentCardIds` / `task.status` / `card.data.status`);`tasksStore.getActiveByCard` 本该是单一真相却零消费者。

**地基结论(已调研确认)**:5 个编辑器所有生成参数的**值**都完整回写了 `card.data`,无 UI-only 漏网参数。所以统一入口「从 card.data 重建请求」**成立**;真正缺的是 `cardRunner` 的**翻译深度**(把 data 值翻成 provider 请求的那段逻辑,目前只活在各 `handleGenerate`)。

## 三、设计原则(P2/P3 共同遵守)

- **单一入口**:`runCard(cardId, opts?)` 是所有生成的唯一发起点。
- **单一真相**:`selectCardBusy` 判断生成中;进度对象仍读 `generatingCards.get`。
- **翻译逻辑下沉为(异步)纯函数**:`buildXxxRequest(card, { onUploadProgress? })`,**编辑器与 cardRunner 共用同一份**。约束校验不弹 toast,返回 `{ ok: true, request } | { ok: false, reason }`,由调用方决定 toast(编辑器)还是 skipped/failed(cardRunner)。
- **编辑器 `handleGenerate` 只剩**:收集 → 调 `buildXxxRequest` → 调 provider(或直接 `runCard`)→ 编辑器特有 UI 善后(几何 resize / toast)。
- **不破坏手点**:每个 build 函数迁移后,先保证编辑器手点逐字等价(`tsc` + 逐族手测),再让 cardRunner 接入。

新增目录:`src/services/generation/`。
