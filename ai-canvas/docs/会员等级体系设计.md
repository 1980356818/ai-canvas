# 会员等级体系设计（试用 / VIP 分级 + 激活码只升不降 + 按级功能门禁）

> 状态：设计稿（待评审）。本文覆盖 **ai-canvas（桌面端）/ ai-canvas-server（服务端）/ ai-canvas-admin（后台）** 三端。
> 决策已拍板：①试用也由激活码授予、带天数 ②会员到期 = 等级清空 + 锁死激活码墙 ③高等级用户用低等级码 = 拒绝不消耗 ④等级与每级功能 **后台数据驱动可配**。

---

## 1. 背景与目标

现状是**纯时间制 + 二元开关**：`user.member_expire_at` 决定有没有会员；有 = 进全功能 app，没有 = 被挡在激活码墙外。激活码只带 `days`，兑换就是叠加时长。**没有任何等级/版本概念，也没有任何功能门禁。**

目标：引入**有序等级**（试用 < VIP1 < VIP2 < VIP3 …），激活码携带等级，按等级开放不同功能；并支持后台随时增删等级、调整每级功能。

---

## 2. 核心概念

### 2.1 等级 = 有序 rank（地基）

所有等级（含试用）统一成一个**有序整数 rank**。"只升不降"、"是否正式版" 全部靠它一行比较：

```
试用 trial = 0   VIP1 = 10   VIP2 = 20   VIP3 = 30 …   (留间隔便于以后插级)
是否正式版 = rank >= 10
```

### 2.2 有效等级 vs 存储等级（关键）

- **存储等级** `user.tier`：上次激活到的等级。
- **有效等级**：`member_expire_at` 未过期才算数；**一旦过期，有效等级 = 无（rank 视为 -1）**，对应"过期等级清空"。
- 过期清空采用**惰性清除**：登录 / 查状态 / 兑换时若检测到已过期，把 `tier` 置空（无需定时任务）。

## 3. 数据模型改动（服务端 MySQL）

### 3.1 新增 `tier_def` 等级定义表（数据驱动的核心）

```sql
CREATE TABLE IF NOT EXISTS `tier_def` (
  `id`          BIGINT       NOT NULL AUTO_INCREMENT,
  `tier_key`    VARCHAR(32)  NOT NULL COMMENT '稳定标识 trial/vip1/vip2…，激活码与用户都引用它',
  `name`        VARCHAR(32)  NOT NULL COMMENT '展示名 试用版/VIP1',
  `tier_rank`   INT          NOT NULL COMMENT '有序等级，越大越高（避开 MySQL 保留字 rank）',
  `is_official` TINYINT      NOT NULL DEFAULT 0 COMMENT '1=正式版 0=试用',
  `features`    JSON         NOT NULL COMMENT '该级能力清单，见 §6',
  `is_active`   TINYINT      NOT NULL DEFAULT 1 COMMENT '0=停用，后台不可选/不下发',
  `sort`        INT          NOT NULL DEFAULT 0,
  `created_at`  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at`  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_tier_key` (`tier_key`),
  KEY `idx_tier_rank` (`tier_rank`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='会员等级定义';

INSERT IGNORE INTO `tier_def` (tier_key,name,tier_rank,is_official,features,sort) VALUES
('trial','试用版', 0, 0, '{"templates":["wf-white-bg","wf-tryon"],"allowBlank":false,"allowImport":false,"maxProjects":2}', 0),
('vip1', 'VIP1',   10,1, '{"templates":"*","allowBlank":true,"allowImport":true}', 1),
('vip2', 'VIP2',   20,1, '{"templates":"*","allowBlank":true,"allowImport":true}', 2),
('vip3', 'VIP3',   30,1, '{"templates":"*","allowBlank":true,"allowImport":true}', 3);
```

### 3.2 `user` 表加 `tier`

```sql
ALTER TABLE `user`
  ADD COLUMN `tier` VARCHAR(32) DEFAULT NULL COMMENT '当前等级 tier_key，过期惰性清空' AFTER `member_expire_at`;
```
（rank 不冗余进 user，运行时 join `tier_def` 取，避免改 rank 要回填。）

### 3.3 `redeem_code` 表加 `tier`

```sql
ALTER TABLE `redeem_code`
  ADD COLUMN `tier` VARCHAR(32) NOT NULL DEFAULT 'vip1' COMMENT '该码激活成的等级 tier_key' AFTER `days`;
```
旧码历史数据默认补成 `vip1`（迁移脚本里 `UPDATE ... WHERE tier IS NULL`），符合"过去发的都是正式会员码"的语义。

### 3.4 `redeem_log` 加前后等级（审计）

```sql
ALTER TABLE `redeem_log`
  ADD COLUMN `before_tier` VARCHAR(32) DEFAULT NULL AFTER `days`,
  ADD COLUMN `after_tier`  VARCHAR(32) DEFAULT NULL AFTER `before_tier`,
  ADD COLUMN `action`      VARCHAR(16) DEFAULT NULL COMMENT 'upgrade/renew/reject' AFTER `after_tier`;
```

> 迁移文件建议放 `ai-canvas-server/src/main/resources/db/` 下新增 `migration_tier.sql`，并同步进 `schema.sql`。

## 4. 兑换"只升不降"算法（服务端 RedeemService）

```
输入: userId, code
codeTier  = code.tier            codeRank = rank(codeTier)
userTier  = 有效等级(user)        userRank = rank(userTier)   // 过期/无会员 → userRank = -1

校验码: 未使用 / 未过期 / 未禁用（沿用现逻辑）

case codeRank > userRank:   // 升级覆盖（含 试用→VIP、VIP1→VIP2、以及过期/新户首次激活）
    user.tier            = codeTier
    user.member_expire_at = now + code.days          // 覆盖：重置时钟（见 §4.1 待定）
    action = "upgrade"

case codeRank == userRank:  // 同级续费
    user.member_expire_at = max(now, member_expire_at) + code.days   // 叠加
    action = "renew"

case codeRank < userRank:   // 低等级码砸到高等级用户
    抛 BizException("您当前已是更高等级会员，无法使用低等级激活码")
    码保持 unused（不消耗）   action = "reject"

成功后: 码置 used + 写 redeem_log(before_tier, after_tier, action)
返回:   { tier, tierName, memberExpireAt, features }
```

要点：
- **过期/新用户**有效 rank = -1，任何码都是 `codeRank > -1` → 走升级分支，直接全新激活。这天然实现"过期后重新输任意码即可恢复"。
- **拒绝分支不消耗码**：`redeem_code` 不置 used，事务里直接抛异常回滚。

### 4.1 ⚠️ 待定：升级时的时间处理

`覆盖` 一词最直白的实现是 **重置时钟**（`now + code.days`，丢弃旧等级剩余天数）。
- 优点：语义最贴"覆盖"，简单。
- 缺点：VIP1 还剩 300 天时升 VIP2（30 天码），会损失 270 天。

可选更厚道方案：升级时 `member_expire_at = max(now, 旧到期) + code.days`（保留时间只换等级）。
**默认按"重置时钟"实现**，此点单独标记，等你确认是否要改成"保留时间"。

## 5. 登录 / 进入判定（服务端 AuthService + 桌面端 App.tsx）

### 5.1 服务端 `login` / `getUserStatus` 下发

在现有 `userVO` 基础上增加字段，并先做**过期惰性清空**：

```
memberActive = member_expire_at != null && member_expire_at.after(now)
if (!memberActive && user.tier != null) { user.tier = null; update }   // 等级清空
restricted = !memberActive                                              // 过期/无会员 → 墙
status     = memberActive ? "active" : (member_expire_at==null ? "inactive" : "expired")

userVO 追加:
  tier      : 有效 tier_key（restricted 时为 null）
  tierName  : 展示名
  tierRank  : 数字
  isOfficial: rank>=10
  features  : tier_def.features（restricted 时为空对象）
```

JWT 里**额外签入 `tier`**（防客户端本地篡改 localStorage 用户对象，见 §8）。

### 5.2 桌面端进入流程（App.tsx）

逻辑基本不变，**激活码墙保留**：

```
未登录            → LoginWindow
restricted(过期/无会员) → RedeemWindow（激活码墙，沿用现状）
有会员            → AuthenticatedApp（进 app，但按 tier 做功能门禁 ← 新增）
```

> 即：试用用户**不被墙**，能进 app，只是功能少；过期才被墙。与你"过期登不上软件 / 锁死弹激活码"一致。

## 6. 功能门禁层（桌面端，新建）

### 6.1 能力清单（features，存 `tier_def.features` JSON，后台可配）

**核心维度 = 允许的项目模板**（试用版的定义就是"只能用预设的几个模板"）。schema：

```jsonc
{
  "templates":   ["wf-white-bg","wf-tryon"],  // 允许的模板 id；字符串 "*" = 全部
  "allowBlank":  false,   // 空白项目 / AI 自由创作（首页 AIPromptInput）
  "allowImport": false,   // 导入 .aicat
  "maxProjects": 2        // 项目数上限（0/省略 = 不限）
}
```

- `templates` 取自客户端 `WORKFLOW_TEMPLATES` 的稳定 id（`wf-white-bg` / `wf-tryon` / `wf-pose-fission` …）；VIP 级一般给 `"*"`。
- 以后要按 VIP 等级细分别的能力（4K / 高级视频 / 智能体…）就往这个 JSON 加键、`can()` 同步加判定，**不用改表结构**。

> **模板目录从哪来**：模板是客户端常量，后台"勾选模板"需要目录(id+名+封面)。v1 方案：客户端启动时把模板清单(manifest)同步到服务端（新增 `/api/app/templates/sync` 或存 `sys_config`），后台读它做勾选，保证单一数据源、不漂移。

### 6.2 草案分级矩阵（**仅起始值，后台可随时改**）

| 维度 | 试用 | VIP1 | VIP2 | VIP3 |
|---|:--:|:--:|:--:|:--:|
| 可用模板 templates | 预设 2-3 个 | 全部 `*` | 全部 `*` | 全部 `*` |
| 空白/自由创作 allowBlank | ✗ | ✓ | ✓ | ✓ |
| 导入 .aicat allowImport | ✗ | ✓ | ✓ | ✓ |
| 项目数 maxProjects | 2 | 不限 | 不限 | 不限 |

> 现在 VIP1/2/3 仅以"模板全开"无法区分，后续按定价在 `features` 里加键细分（如高级视频模型只给 VIP2+、4K 只给 VIP1+）。框架已支持，**加键即可，不改表**。

### 6.3 实现

- 新建 `src/stores/entitlementsStore.ts`（或并入 authStore）：保存 `features`，提供：
  - `can(key): boolean`（布尔能力）
  - `allowCard(type): boolean`（卡片类型）
  - `limit(key): number`（数值上限）
- **两处拦截**（UI 拦 + 入口拦，双保险）：
  1. **UI 层**：卡片创建菜单 / 模型下拉 / 4K 档 / Agent 面板入口 / 导出按钮 等——无权限则**置灰 + "升级解锁"角标**，点击弹升级提示。
  2. **生成入口**：`src/services/generation/*`、`cardRunner`、`groupRunner` 真正发请求前再 `can()` 校验一次，挡住绕过 UI 的路径。
- **升级入口**：把 `RedeemWindow` 从"只在墙上出现"扩展为**可在 app 内随时打开的弹窗**（点"升级解锁"即弹），输码走同一 `redeem` 流程；成功后刷新 `features` 立即解锁，无需重登。

## 8. 安全说明（必须知情）

桌面端的生成请求是**直连上游 AI（极境等），不经过这台 license 服务器**。因此 §6 的功能门禁本质是**客户端强约束，技术上可被破解**（改本地代码/数据即可绕过）。

- v1 取舍：做**客户端门禁 + 把 `tier` 签进 JWT**（客户端展示信任服务端签发值，localStorage 改不动 JWT 声明），挡住普通用户。
- 要做到**真不可绕过**：需把生成请求改为经服务端代理鉴权后再转上游——工作量大，**留作后续**，本设计预埋 `features` 服务端下发，不阻碍以后切代理。
