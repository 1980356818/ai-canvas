# 「帮我写」分镜脚本节点 — 设计与施工图

> 复刻第三方「帮我写」功能（连入素材 → 视觉分析 → 三步向导 → 生成分镜脚本），适配 ai-canvas 节点画布。
> 专用于 AI 视频创作（电商带货 / 种草 / 卖点钩子）。
> 状态：**设计定稿，待施工**。本文是唯一权威施工图。

---

## 0. 一句话结论（先看这个）

> **新节点 `ai_script`（帮我写） = `ai_chat` 的全套 I/O 底座 + 一个三步向导 + 一条固定提示词流水线。**
> 输入（图/视频/文本连线）、计费（网关按 token）、输出（`data.result` 文本下游传播）**全部复用 `ai_chat` 既有通路**，零新增下游管线。真正要写的只有「向导 UI + 分析/生成两次调用 + JSON 解析」。

这条结论来自两个关键代码事实：

1. **`ai_chat` 已经做到本节点需要的全部 I/O**（`src/lib/dataFlow.ts`）：它接受连入的图片（`refImages`）、视频（`refVideos`）、文本（`upstreamTexts`），跑视觉 LLM，并把结果写进 `data.result` 向下游输出文本。本节点要的「连素材 → 分析 → 出文本」与之**逐字段同构**。
2. **分镜脚本本质是文本**（用户拍板）：第 3 步「应用脚本」= 把生成的分镜序列化成 markdown 写进 `data.result`，`extractOutput` 当 `kind:"text"` 原样下发——和 `ai_chat` 完全一致，下游视频/图片卡无需任何改动即可读取。

## 1. 范围与非目标

**做：**
- 新增 `ai_script` 卡型（标签「帮我写」，副标题「分镜脚本」）。
- 连入图片/视频/文本素材 → 第 1 步视觉分析出「商品洞察」（可编辑）。
- 第 2 步「脚本配置」表单（业务/语言/内容类型/拍摄方式/参考视频开关/补充说明）。
- 第 3 步生成「逐秒分镜脚本」并预览，可重新生成。
- 「应用脚本」把脚本文本写进 `data.result`，下游照 `ai_chat` 文本通路自动读取。
- 计费透明弹窗（预估 + 不再提示 + 失败不扣费说明）。

**不做（本期）：**
- 不复刻第三方页面的视觉/布局，只复刻功能。
- 不做「一键在画布自动铺开分镜→视频卡生产线」（用户明确暂不要，§10 留接口）。
- 不引入服务端工作流；分析与生成都走客户端编排 + 现有 JiJing 网关（与 `ai_chat` 同一条路）。
- 不新增 SQLite 迁移（见 §6）。

## 2. 关键架构决策

| 维度 | 决策 | 依据 |
|---|---|---|
| 卡型 | 新增 `ai_script`（用户要求「这是新节点」） | `types/card.ts` 联合类型 |

## 3. 数据模型

存于 `card.data`（`src/features/script/types.ts` 新建）。`result` 是下游唯一真相，其余为向导态/预览用。

```ts
import type { RefImageEntry } from "@/config/model-ref-images";

interface VideoRefEntry { url: string; sourceCardId?: string }
interface MediaAttachment { url: string; displayUrl?: string; kind: "image" | "video" }

export interface ScriptCardData {
  // ── 与 ai_chat 同构的 I/O 底座（dataFlow 注入/抽取直接复用）──
  model?: string;            // 视觉 CHAT 模型（分析步用，须 modelSupportsVision）
  provider?: string;
  refImages?: Record<string, RefImageEntry>;  // 连入的商品图（按槽位）
  refVideos?: VideoRefEntry[];                 // 连入的参考视频（≤3）
  directMedia?: MediaAttachment[];             // 手动上传的图
  upstreamTexts?: Record<string, string>;      // 连入的文本上下文
  result?: string;           // ★ 最终分镜脚本（markdown）— 下游读这个

  // ── 帮我写专属态（逐步落库，支持关弹窗后恢复）──
  insights?: ProductInsights;   // 第1步产物，可编辑
  config?: ScriptConfig;        // 第2步表单
  script?: StoryboardScript;    // 第3步结构化脚本（用于预览/重生）
  refVideoBreakdown?: string;   // 可选：参考视频拆解结果
  _wizardStep?: 0 | 1 | 2 | 3;  // 恢复点（0=计费确认）
  _analyzedAt?: string;
  _resultStale?: boolean;       // 与 ai_chat 同义：result 已过时待重生
}

export interface ProductInsights {
  productName: string;        // 商品名称
  category: string;           // 商品类目
  features: string[];         // 产品特性
  sellingPoints: string[];    // 核心卖点
  targetAudience: string[];   // 目标人群
  usageScenarios: string[];   // 使用场景
  materials: { ref: string; description: string }[]; // 素材分析（逐图/逐视频描述）
}

export interface ScriptConfig {
  business: "ecommerce" | "local_store" | "on_site" | "education"; // 业务场景
  language: "auto" | "zh" | "en" | "ja" | "de" | "fr";            // 语言
  contentType: "auto" | "selling" | "planting" | "hook" | "drama" | "vlog"; // 内容类型
  shootingStyle: "auto" | "desktop_unbox" | "real_person" | "one_take" | "motion" | "brand_tvc"; // 拍摄方式
  useReferenceVideo: boolean; // 参考视频拆解开关
  notes?: string;             // 补充说明
}

export interface StoryboardScript {
  overview: { styleKeywords: string[]; note: string };  // 视频总览
  sceneLighting: { scene: string; lighting: string };   // 场景与光线
  shots: ShotBreakdown[];                                // 逐秒镜头拆解
}

export interface ShotBreakdown {
  timeRange: string;     // "0-3s"
  shotType: string;      // 景别/角度
  cameraMove: string;    // 运镜
  sceneDialogue: string; // 场景与对白
  voiceover: string;     // 口播旁白
  audioBgm: string;      // 音效/BGM 节奏
}
```

**为什么保留 `script`（结构化）又写 `result`（文本）？**
`script` 驱动截图里的逐镜卡片预览 + 「重新生成」；`result` 是序列化后的 markdown，是 I/O 与持久化的真相。下游只认 `result`。两者由 `lib/scriptSerialize.ts` 单向同步（`script → result`）。若要极简也可只留 `result`，但会失去结构化预览。

## 4. 向导流程与计费弹窗

向导是**全屏 modal**（`features/script/ScriptWizard.tsx`），由 `uiStore.scriptWizardCardId` 驱动（仿 `cardTaskPanelCardId`），在 App 根渲染为浮层。左侧步骤栏，右侧内容区。

```
┌ 计费确认（_wizardStep=0，可「不再提示」跳过）
│   预计消耗（透明预估）/ 计费明细按将运行步骤列 / 失败不扣费 / 取消·继续
├ ① 分析我的素材（_wizardStep=1）
│   收集连入 图(refImages+directMedia) + 视频(refVideos) + 文本(upstreamTexts)
│   → 视觉调用 #1（固定提示词，要 JSON）→ ProductInsights
│   → 渲染：素材分析(逐图描述) + 商品洞察(6 组可增删的 chip)
├ ② 脚本配置（_wizardStep=2，纯表单，无调用）
│   业务/语言/内容类型/拍摄方式 胶囊 + 参考视频开关 + 补充说明
├ ③ 预览视频脚本（_wizardStep=3）
│   (可选) 参考视频拆解 → 视觉调用 #1.5
│   → 生成调用 #2（insights+config 喂入，要 JSON，流式）→ StoryboardScript
│   → 渲染：视频总览 + 场景与光线 + 逐秒镜头拆解
│   → 「重新生成脚本」重跑本步 / 「应用脚本」序列化→result→关闭→下游传播
└
```

**逐步落库**：每步完成即 `updateCardData(cardId, { insights / config / script, _wizardStep })`，关弹窗再开能从 `_wizardStep` 恢复（企业级健壮性）。

**计费弹窗（截图 1）适配**：
ai-canvas 客户端**无余额概念**（`entitlements.ts` 仅模板门禁；真正计费在网关按 token 结算）。所以弹窗是**透明预估**而非硬扣费门：
- 按「本次将运行的步骤」列预估：`分析素材`（必跑）、`参考视频拆解`（仅开关开+有视频时）、`生成脚本`（必跑）。
- 每步预估 = 该 CHAT 模型 token 单价 × 经验 token 量（`services/pricing` 的 `inputPer1m`/`outputPer1m`），给一个区间或「≈X 元」。无法精确时退化为固定展示档。
- 「不再提示」→ `settings` 持久化键 `script.skipCostConfirm`，下次直接进第 1 步。
- 「失败不扣对应积分」属实：网关只对成功返回的上游调用计费。
- 「当前可用余额」：**仅当** `AuthUser` 暴露余额字段时显示（待核 `platform/auth.api`），否则不显示该行，避免假数据。

## 5. 提示词流水线

`src/lib/scriptPrompts.ts` 集中三段系统提示词 + 期望 JSON schema。**全部要求严格 JSON 输出**，由 `lib/scriptParse.ts` 防御式解析（去 ```json fence / try-catch / 字段兜底 / 失败可重试一次）。前例：`frame_extractor` 已在消费 `ai_chat` 的分镜 JSON 文本（`dataFlow.ts:39,697`），JSON-from-chat 在本仓是成熟模式。

**① 分析提示词（视觉）** — 输入：素材图/视频帧 + 可选文本上下文。输出：
```json
{
  "productName": "...", "category": "...",
  "features": ["..."], "sellingPoints": ["..."],
  "targetAudience": ["..."], "usageScenarios": ["..."],
  "materials": [{ "ref": "图1", "description": "..." }]
}
```
系统提示词要点：你是电商短视频策划，只依据可见素材客观提炼，不臆造参数；中文；严格输出上述 JSON，无多余文字。

**①.5 参考视频拆解（视觉，可选）** — 输入：`refVideos`。输出一段结构化文本（节奏/景别序列/钩子结构），作为第 3 步的「框架参考」。

**② 生成提示词（文本，流式）** — 输入：`insights` + `config`（+ 可选拆解）。输出：
```json
{
  "overview": { "styleKeywords": ["..."], "note": "..." },
  "sceneLighting": { "scene": "...", "lighting": "..." },
  "shots": [{
    "timeRange": "0-3s", "shotType": "...", "cameraMove": "...",
    "sceneDialogue": "...", "voiceover": "...", "audioBgm": "..."
  }]
}
```
系统提示词按 `config` 动态拼：内容类型/拍摄方式/语言映射成自然语言约束；时长默认 30s 拆 6–10 镜；口播旁白口语化。

## 6. dataFlow 集成（精确改动清单）

**核心策略：`ai_script` 在 `dataFlow.ts` 所有判定处「与 `ai_chat` 同档」。** 逐处：

```ts
// ① outputKindOf（line ~20）：输出文本
case "text": case "sticky_note": case "ai_chat": case "ai_script": return "text";

// ② canKindFlowInto（line ~32）：接受 文本/图片/视频（照 ai_chat）
case "ai_chat": case "ai_script": return kind === "text" || kind === "image" || kind === "video";

// ③ REF_IMAGE_TARGETS（line 12）：加入
const REF_IMAGE_TARGETS = new Set(["ai_image", "ai_multiangle", "ai_chat", "ai_script"]);

// ④ getRefSlots（line 58）：ai_script 用 chat 槽位
return (target.type === "ai_chat" || target.type === "ai_script")
  ? getRefSlotsForChatModel(model) : getRefSlotsForModel(model);

// ⑤ targetTypeLabel（line 45）：
case "ai_script": return "帮我写节点";

// ⑥ extractOutput（line 344）：读 result（与 ai_chat 同分支，合并 case）
case "ai_chat":
case "ai_script": {
  const result = d.result as string | undefined;
  if (result && !result.startsWith("错误:")) return { kind: "text", text: result };
  return { kind: "none" };
}

// ⑦ injectIntoCard（line 398）：新增 case "ai_script"，复制 ai_chat 分支
//    （text→upstreamTexts / image→refImages 走 getRefSlotsForChatModel / video→refVideos≤3）

// ⑧ canAcceptConnection（line 67）：把 ai_chat 专项分支扩展含 ai_script
//    - line 147「video → ai_chat」：改成 (ai_chat || ai_script)
//    - line 164 起「image → ...」末尾 getRefSlots 分支已按 type 走，天然覆盖 ai_script
```

> ⚠️ **同步铁律**（文件顶部注释 line 14-16 明确）：`outputKindOf` 与 `canKindFlowInto` 是验证与注入的共同基准，漏改一处 = 「能连线但没反应」。本清单 ①②⑥⑦⑧ 必须一起改。

## 8. 复用生成底座（buildChatRequest 的最小改动）

分析/生成两次调用都要「连入素材 → 多模态 user content」，这正是 `buildChatRequest`（`services/generation/buildChatRequest.ts`，全仓**唯一对话翻译层**）做的事：`serializeForApi` 内联保序 + `uploadMediaBatch` 并行上传 + `modelSupportsVision` 判定 + `<upstream_context>` 前缀。

**推荐做法（加性、向后兼容、保持单一翻译层）**：给 `buildChatRequest` 增可选 overrides——

```ts
export interface BuildChatRequestOptions {
  onUploadProgress?: (...) => void;
  systemPromptOverride?: string;  // 覆盖 _systemPrompt/默认（分析、生成各传各的）
  promptOverride?: string;        // content 为空时的触发指令（如「请分析以上素材」）
  maxTokens?: number;             // 分析步可调小
}
```
仅需在读取 `content`/`systemPrompt` 两处让 override 优先，其余逻辑零改。`script` 服务这样调：

```ts
// 分析：视觉，短，要 JSON，非流式
const built = await buildChatRequest(card, {
  systemPromptOverride: ANALYZE_SYSTEM_PROMPT,
  promptOverride: "请基于以上素材输出商品洞察 JSON。",
  maxTokens: 4096,
});
const provider = modelService.resolveProvider(built.request.model, built.providerId);
const { content } = await provider.chat(built.request);   // 或 streamChatToResult 不绑卡
const insights = parseInsights(content);

// 生成：文本为主，长，流式（进度落卡 + 向导）
const genCard = { ...card, data: { ...card.data, content: buildGenPrompt(insights, config), refImages: undefined, refVideos: undefined, _systemPrompt: undefined } };
const built2 = await buildChatRequest(genCard, { systemPromptOverride: GENERATE_SYSTEM_PROMPT, maxTokens: 65536 });
const { content: raw } = await streamChatToCard(provider, built2.request, card.id);
const script = parseScript(raw);
```

> 备选：抽 `assembleMultimodalContent(card, opts)` helper 给两路共用——更纯但是改动面更大。**首选 overrides**。

调用一律包进 `runEditorGeneration(card, { setError, run })`（`services/generation/runEditorGeneration.ts`）拿到统一的 API Key 预检 / 进度锁 / `friendlyError` 兜底 / `finally` 清进度（截图里「失败不扣费、可重试」就靠它）。

## 9. 健壮性 / 可观测 / 持久化

- **逐步落库**：每步产物即时 `updateCardData` + `autoSave.markDirty`；`_wizardStep` 支持关弹窗后恢复。
- **进度**：生成步走 `streamChatToCard`，卡片进度条 + 向导内同时显示流式字数（`uiStore.generatingCards`）。
- **错误**：复用 `runEditorGeneration` 的 `friendlyError`；失败**不写 `result`**（保留旧脚本，置 `_resultStale`）。
- **JSON 不稳**：`scriptParse` 去 fence + try-catch + 字段兜底；解析失败自动重试 1 次（提示词追加「上次输出非合法 JSON，请仅返回 JSON」），再失败则报错可手动重生。
- **并发/取代**：向导是前台 modal，无需 `AsyncTask` 保活机器（那是为后台 fire-and-forget 卡设计）；但最终 `result` 写入走同一 `updateCardData → dataFlow watcher → 下游传播` 路径，零特例。
- **持久化无迁移**：`card.data` 是 JSON blob，`rowToCard` 盲转型（`mappers.ts:35`），`cards.type` 列 TEXT 无 CHECK → 新类型与新字段都自动持久化。

## 12. 风险与坑（务必先读）

1. **`modelDefaults` 漏注册 `ai_script`** → `resolveDefaultModelForCardType` 返回 `null` → `buildChatRequest` 报「无法解析默认对话模型」。**最易漏，§7 #3。**
2. **`dataFlow` 同步铁律**：`outputKindOf`/`canKindFlowInto`/`injectIntoCard`/`extractOutput`/`canAcceptConnection` 必须一起加 `ai_script`，漏一处 = 「能连线但没反应」或注入崩。
3. **`canAcceptConnection` 的 `ai_chat` 专项分支**（line 147 video→ai_chat）需显式含 `ai_script`，否则连视频进帮我写卡会被拦。
4. **画布渲染契约**（`CLAUDE.md`）：`ScriptCard` 不得在 `.vp-pan-layer` 子树内放常驻动画（#6）；不得 `useCardStore(s=>s.cards)` 订阅整 Map（#5/#7）。向导是画布外 modal，安全。
5. **视觉模型**：分析步必须选 `modelSupportsVision` 的 CHAT 模型（默认 `gemini-3.1-pro-preview` 可视觉）；非视觉模型时 `buildChatRequest` 会 `warning` 忽略媒体——UI 应过滤模型选择器或提示。
6. **计费弹窗别假装有余额**：客户端无余额真值，弹窗只做透明预估；「可用余额」仅在确认 `AuthUser` 有该字段后接入。
7. **result 体量**：脚本 markdown 可能较长，作为下游 ai_video 的 prompt 偏大——P3 可加「仅取某镜口播/画面」的下游裁剪，本期 result = 全文。
